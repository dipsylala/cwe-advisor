# CWE-94: Improper Control of Generation of Code ('Code Injection') - Java

## LLM Guidance

Code injection in Java occurs when untrusted input is evaluated through scripting engines (`javax.script.ScriptEngine` with JavaScript, Groovy, or MVEL), Groovy's `GroovyShell`, Spring Expression Language against a `StandardEvaluationContext`, or template engines without sandboxing. The `ScriptEngine` API is particularly dangerous because it can be exposed unintentionally through configuration-driven features. Replace dynamic code evaluation with static logic, a lookup table, or a purpose-built sandboxed evaluator. SpEL is not that evaluator (see Key Principles); moving an existing SpEL finding to `SimpleEvaluationContext` is the smaller change while the expression source is taken out of the request.

## Key Principles

- Remove or disable `ScriptEngine` access to untrusted input entirely - there is no safe way to sandbox Nashorn/Rhino for arbitrary user expressions
- Replace dynamic script evaluation with predefined logic: switch statements, strategy patterns, or configuration-driven dispatch tables
- If a user-configurable expression language is required, use a purpose-built, sandboxed evaluator - Apache Commons JEXL with a `JexlSandbox` built deny-by-default via `new JexlSandbox(false)`. `JexlSandbox` lives in `org.apache.commons.jexl3.introspection`, not beside `JexlBuilder` in `org.apache.commons.jexl3` - an import from the latter does not compile. SpEL is not the one to reach for: Spring states that `SimpleEvaluationContext`'s restriction is "provided on a best-effort basis and does not guarantee that expression evaluation is safe", and that evaluating an expression from an untrusted source "is inherently dangerous and should generally be avoided" whichever `EvaluationContext` is used
- Never pass user input to Groovy's `GroovyShell.evaluate()`, `GroovyClassLoader.parseClass()`, or `GroovyScriptEngine` (`groovy.lang.GroovyShell`, `groovy.lang.GroovyClassLoader`, `groovy.util.GroovyScriptEngine`)
- Keep the language the stored expressions are written in. Replacing a JavaScript engine with JEXL changes the grammar and semantics every saved rule was written against (JEXL 3.4.0 added `===` and `!==`, and it does have arrow-syntax lambdas, but not template literals, regex literals, `typeof`, or JavaScript's `==` coercion rules), and nothing checks the stored rules against the new parser until one is evaluated; if the stored rules are JavaScript, the fix is a JavaScript engine that denies host access, not a different language - a language change is a migration to state separately, with every stored rule re-validated under the new engine
- For Spring Expression Language, evaluate against a `SimpleEvaluationContext` rather than a `StandardEvaluationContext` (both in `org.springframework.expression.spel.support`): the standard context permits type references (`T(java.lang.Runtime).getRuntime().exec(...)`), constructors and bean references, and the simple one is limited to property access - broader than it sounds, since SpEL resolves a bare name through the record-style plain accessor on any class, so a `secret()` method on the root is invoked by writing `secret`, and `secret.length` chains off it (reproduced on 6.2.19; the explicit `secret()` is refused). The root's whole public zero-arg surface is reachable. Take 6.2.19 or 7.0.8, which fix CVE-2026-41850/41851/41852, the last being zero-arg invocation "even within restricted or read-only contexts"; 6.1 and 5.3 have no OSS fix. Build it with `SimpleEvaluationContext.forReadOnlyDataBinding().build()` for property reads on the root object, and hand the root object to `expression.getValue(context, rootObject)` or to the builder's `withRootObject(...)` - `setRootObject()` exists only on `StandardEvaluationContext`, so calling it on the simple one does not compile. `forPropertyAccessors(...)` registers only the accessors passed to it, so called with none it throws `SpelEvaluationException` on every property read, the legitimate expressions included
- `ScriptEngineManager.getEngineByName("JavaScript")` returns `null` on JDK 15 and later unless a script engine was added back as a dependency, so a finding on that line may be dead code - confirm the runtime before treating it as live, and check whether the null is dereferenced
- Where an engine is genuinely required, restrict what it can reach rather than filtering the script text, and be concrete about what enforces that - a class loader is not a permission boundary, and the SecurityManager that historically supplied one was deprecated for removal by JEP 411 and permanently disabled in JDK 24 by JEP 486. On a current JDK the containment has to come from outside the process: a separate JVM under OS-level limits, or a container

## Taint Sinks

`ScriptEngine.eval()`, `GroovyShell.evaluate()`, `GroovyClassLoader.parseClass()`, `GroovyScriptEngine`, `MVEL.eval()`, `SpelExpressionParser.parseExpression()`, `Expression.getValue()`

## Remediation Steps

- Locate `ScriptEngine.eval(userInput)`, `GroovyShell.evaluate(userInput)`, or similar dynamic compilation calls
- Replace with a lookup table or strategy pattern mapping known-safe identifiers to predefined Java methods
- If a user-visible expression language is a genuine product requirement, evaluate Apache Commons JEXL with `new JexlSandbox(false)` - deny-by-default - and allow only narrow concrete classes by name; `new JexlSandbox(true)` is allow-by-default and still reads as sandboxed in review. Object construction is a separate control, `JexlFeatures.newInstance(false)` via `JexlBuilder.features(...)` - but state the default: on 3.7.0 the builder already refuses `new(...)`, and the default `JexlPermissions` already evaluate `Runtime` and `Class.forName` to `null` with no sandbox at all. Note that `sandbox.allow(...)` grants permission but not reach - an allowed class is callable only if the evaluation context exposes it via `JexlBuilder.namespaces(...)` or a context variable, so an allow entry on its own changes nothing about what the expression can name
- Validate the expression text only where the application defines its format, and say what that rejects - the sandboxed evaluator or lookup table is what closes the injection
- Add integration tests that attempt to inject OS commands or class-loading expressions, and assert on the value returned, and pick a probe the default permissions allow: a sandbox denial evaluates to `null` rather than throwing, and on 3.7.0 a `Runtime` or `forName` probe is already `null` with no sandbox, so neither a throws-assertion nor that probe shows the sandbox was wired. Use something the defaults permit and the allowlist must deny, such as `s.length()` on a `String` the sandbox omits
- Review build plugins and reflection-heavy frameworks (e.g., BeanShell, MVEL) for similar exposure
